# Harness 治理的本质：从打分到意图对齐

> 打分解决的是"底线问题"（不要低于某个标准），不是"方向问题"（该往哪走）。

## 1. 打分机制的天然局限

### 分数是度量，不是理解

```
文件 800 行 → 扣分
测试覆盖率 90% → 加分
lint 通过 → 加分
总分 85 → 放行
```

这套逻辑回答不了真正重要的问题：

- 这个改动破坏了原有设计意图吗？
- 这个抽象是正确的，还是只是恰好通过了检查？
- 两段代码都"合规"，但哪个更符合项目的演进方向？

### 度量的三层本质

| 层级 | 问的问题 | Harness 打分能答吗 | 举例 |
|------|---------|-------------------|------|
| 度量层 | 文件行数？覆盖率？lint？ | 能 | 文件超 1000 行扣分 |
| 结构层 | 改动跨越了架构边界吗？ | 部分能 | review-triggers 有跨边界检测 |
| 语义层 | 这个改动符合设计意图吗？ | **不能** | 缓存策略和"local-first"原则矛盾 |
| 意图层 | 当初为什么这样设计？现在还成立吗？ | **不能** | ADR 的前提假设是否还成立 |

**度量层是低级错误防线，语义层和意图层才是工程质量的核心。**

### 打分的正确用法

打分不是没用，但它的价值在**排除法**而非**判定法**：

```
正确用法：分数 < 80 → "一定有问题，先别合"
错误用法：分数 ≥ 80 → "没问题了，可以合"

分数是"必要条件"，不是"充分条件"。
```

类比：体检指标异常说明一定有问题，但指标正常不代表你健康。

## 2. 比打分更接近本质的治理机制

Routa 已有一些组件在做更深层的事，只是没被系统化：

### ADR — 设计意图的锚点

```
ADR 0003: Workspace-first scope
  → 任何新功能如果没有 workspace 上下文，就是违规
  → 这不是分数能判定的，是对齐问题
```

ADR 记录"为什么这样设计"。打分不关心原因，ADR 关心。

### Artifact Gate — 二元判定而非模糊打分

```
Review 列要求"验证报告"
  → 有就是有，没有就是没有
  → 比分数阈值更清晰、更可追溯
```

### Lane Handoff — Agent 间的交叉验证

```
Review Agent 问 Dev Agent："你的环境怎么配的？"
  → 比"Dev 阶段得分 85"更能暴露 Dev 阶段的问题
  → 上下文传递本质上是跨角色的交叉审查
```

## 3. 如果要深入本质：意图治理闭环

真正的工程治理应该回答的问题是：

```
不是问：  "这个 PR 得了多少分？"
而是问：  "这个改动遵守了哪条架构决策？违反了哪条？为什么？"
         "这个改动的意图，在 ARCHITECTURE.md 里有对应的设计依据吗？"
         "做完之后，项目的架构文档需要更新吗？"
```

### 四个可能的方向

#### 3.1 意图回溯

每个 Agent 产出物关联到它依据的设计决策。不关联的就需要人审。

```
Agent 产出：新增了 Redis 缓存层
  → 关联到哪条 ADR？→ 没有关联
  → 标记：需要人工审查（无人认领的架构决策）
```

#### 3.2 架构漂移检测

代码结构和 ARCHITECTURE.md 描述的是否一致。不一致时追问：是代码错了，还是文档过时了？

```
ARCHITECTURE.md 说："所有 Agent 交互走 ACP 协议"
代码里：新增了直接 HTTP 调用 Agent 的路径
  → 漂移！是代码要改，还是架构文档要更新？
```

#### 3.3 决策压力测试

新改动对已有 ADR 的前提假设有冲击吗？冲击了就要重新讨论。

```
ADR 0002 的前提："所有 Agent 走 ACP 适配"
新功能：引入了 WebSocket 直连 Agent
  → ADR 0002 的前提被挑战了
  → 触发：ADR 需要修订或创建新 ADR
```

#### 3.4 影响半径可视化

这个改动会影响哪些边界？哪些下游 Agent 会受影响？

```
改动：修改了 ACP session/new 的参数结构
影响半径：
  → kanban/agent-trigger.ts（创建 session 的地方）
  → background-worker/index.ts（派发任务的地方）
  → Rust AcpManager（桌面端对等实现）
  → 3 个下游 Agent 角色可能受影响
```

## 4. 总结

| | 打分治理（现状） | 意图治理（方向） |
|---|---|---|
| 回答的问题 | "够不够格？" | "方向对不对？" |
| 判定方式 | 阈值（分数 ≥ 80） | 对齐（代码 ↔ ADR ↔ 架构文档） |
| 适用场景 | 拦截低级错误 | 保证架构演进的一致性 |
| Agent 的角色 | 拿到分数后自己判断 | 被约束在决策框架内行动 |
| 人的角色 | 看分数决定放不放 | 审查意图对不对，而非分数高不高 |

打分是**浅层治理**，意图对齐是**深层治理**。两者都需要，但不应把打分当作结清依据。Harness 的打分适合做"不合格拦截"，真正结清靠的是设计意图的持续对齐。

Routa 现有的 ADR 体系、Artifact Gate、Lane Handoff 已经比纯打分更接近本质，下一步可能是把这些串成一个系统化的"意图治理"闭环。
